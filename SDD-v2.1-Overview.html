Token 生命週期 (三種 Token,不同中介層驗證)

Session Token
效期 90 天
App 啟動時換新,玩家無感。Bootstrap 場景背景呼叫 POST /players。
Sense Token
效期 30 分鐘
進入 150m 核發;剩 1–2 分鐘且仍在範圍內時靜默重呼 /sense。
Encounter Token
效期 15 分鐘
50m 召喚成立核發;過期即任務嘗試失敗,不續期。
儲存於 Android Keystore;不得使用 PlayerPrefs。三種 token 後端須用不同中介層驗證,不可共用邏輯。

契約單一真相來源:Code-first + CI 契約閘門

拆兩個 repo 的代價是「後端改契約、客戶端沒跟上」。3 天 Sprint 節奏下這會頻繁發生,採 code-first + CI 閘門,不採 pure schema-first (FastAPI 反向生成 server code 摩擦過大)。

#Unity 端硬規則理由
1只生成 DTO model,不生成 HTTP clientGenerator 預設 HttpClient 版本不適用 Unity;ApiClient.cs 維持手寫 UnityWebRequest
2使用 Newtonsoft.Json,不得使用 JsonUtilityJsonUtility 不支援 Dictionary 與 nullable,無法處理 unlock_story: {...} | null
3landmark-photo 端點手寫multipart/form-data,codegen 產物不可直接使用
4Generated/ 檔頭標註 DO NOT EDIT,CI 檢查防止手改後被下次生成覆蓋
5Enum 寬鬆解析,未知值 fallback 而非拋錯後端新增 enum 值對舊版 App 屬破壞性變更
版本相容原則 · 只加不減: 後端可新增欄位,不得刪除或改名;客戶端忽略未讀欄位。破壞性變更必須開 /api/v2,舊版保留過渡期。契約凍結時點:Phase 1。
05

內部介面 · 後端模組間

模組邊界的三個核心設計:內容生成 vs 排程分離、共鳴值判定順序、記憶 schema 所有權。
Dialogue Path

當日情境:內容 vs 排程分離

內容生成 (腦袋 B9) 與排程/快取/serve (身體 S10) 拆分。身體透過 GET /daily-event 對外,腦袋 nightly 產出寫入快取。
Resonance Path

共鳴值:身體先判定 → 腦袋後敘事

身體 S5 判定達標 → 呼叫腦袋 B11 生成解鎖敘事。順序不可顛倒 — 不能由 LLM 決定達標與否。
Face ↔ Brain

對嘴介面:只剩音檔 URL

v1 (音檔 + viseme JSON) → v2.1 (只剩 audio_url)。臉自行做 MFCC 分析,腦袋不再產出時間軸。

記憶 Schema 所有權

Body owns
結構化欄位
任務進度、共鳴值、Token 生命週期、玩家身分、Sense/Encounter 事件紀錄。Postgres 標準表。
Brain owns
語意化欄位
對話記憶 (短期 Redis / 長期 pgvector)、記憶摘要、當日情境內容。僅靠 player_id 與身體關聯。
Schema 硬約束 (不變): 不得新增任何 location_history / movement_trace 類型的表。原始 GPS 只在驗證期間使用後即丟棄,不形成軌跡。

Phase 0

技術驗證

2 Sprint / 6 天
5 個 POC 必須全過才進 Phase 1:
  • P0-A 資產可行性 (臉):Mixamo 自動綁骨成功、四肢無崩壞、JawOpen shape key 可製作、單隻清理 < 4 小時。未通過即切換 CC4 備援。
  • P0-B 3DoF 方位穩定性 (身體):龍山寺現場原地旋轉,角色方位偏移 < 15°;含校正流程。
  • P0-C Unity 繁中 IME (身體):Android 實機中文輸入法不跳版、不吃字、不遮擋輸入框。
  • P0-D 對嘴+效能 (身體+臉):中階實機連續 5 分鐘 ≥ 30fps。
  • P0-E 後端環境 (腦袋):docker-compose 起 Postgres+Redis,3 個核心端點通。
P0-B/C/D 皆由身體負責,建議順序 B → C → D 避免並行。Phase 0 結束後,Phase 1–7 需複審 — P0-A 結果會改變整條資產產線定義。

3DoF 實境疊層原理

明確排除真 AR (SLAM / ARCore / ARKit / Geospatial),改用陀螺儀 + 電子羅盤 3DoF 感測器定向 — 角色固定在某方位角,需轉動手機才看得到。
❌ 不採用

0DoF 純疊層

手機轉動時角色永遠在螢幕正中。缺乏尋找感,無方位互動。
✅ v2.1 採用

3DoF 感測器定向

角色固定在某方位角,需轉動手機才看得到。方向指示器引導轉向。
❌ Roadmap

6DoF SLAM

角色釘在世界座標,可繞行。需 ARCore/ARKit,認證裝置白名單。

實作原則

  1. 每個靈魂在 spirits 表設定 bearing_deg (真北 0°,順時針)
  2. 讀取 Input.compass.trueHeading 取得手機朝向
  3. 角色螢幕水平位置 = f(靈魂方位角 − 手機朝向);超出視野不繪製
  4. 螢幕邊緣顯示方向指示器引導轉向
  5. Input.gyro.attitude 補償俯仰/翻滾,維持角色水平站立
  6. 角色縮放依 GPS 距離插值 (沿用 v1 漸顯機制),非相機實算透視
已知取捨

3DoF 無法做到的事

  • 無遮擋 (角色會穿過真實物體)
  • 無真實景深
  • 羅盤受都市磁干擾
  • 玩家平移時無視差
必做緩解手段

非加分項,是必要項

  • 接地 blob shadow (不透明度約 0.3)
  • 相機畫面平均色溫匹配 ambient light
  • 邊緣柔化
  • 靈魂感 shader (§9 定義)
