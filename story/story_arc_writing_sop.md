# 主線劇情（story arc）撰寫 — 建立流程（SOP）

> 適用對象：任何要寫一條新主線劇情的人（不限 Lead）
> 這份流程產出的是**劇情內容規格文件**，不是正式資料。正式資料的終點是 `brain.story_arcs` / `brain.story_beats` / `brain.resonance_unlockables`，中間還要經過 Lead 審核與 YAML 轉檔。
> 姊妹文件：`landmark/landmark_research_sop.md`（地標史實）。兩者的關係見 §1。

---

## 0. 這一步在整個內容管線裡的位置

```text
① 史實蒐集（landmark/*.md）           ← 地標 SOP 負責
② 寫入 brain.landmark_souls / city_souls
③ 人格草稿（archetype / speech_style / taboos...）
④ 人工審核 → flip character_personas.active = true
⑤ 建立 spirits 記錄（召喚點座標、半徑）
─────────────── 以上是「靈魂存在」的前提 ───────────────
⑥ 主線劇情設計 ← 這份 SOP 從這裡開始
⑦ 寫成 arcs/{arc_id}.yaml
⑧ 匯入器驗證（DAG 檢查、引用檢查）→ 寫入 brain.story_arcs / story_beats
⑨ 建立對應的 quests 與 media_assets
⑩ 地理圍欄 GeoJSON 匯入 brain.districts
```

**①–⑤ 沒完成就不要開始寫 arc。** 不是流程潔癖——`story_beats.character_id` 是指向 `brain.characters` 的**真外鍵**（同一個 schema 內，不是值關聯），角色不存在時那一列插不進去。劇情寫得再好，資料也進不了資料庫。

> **跟 `event/` 的分界**：`event/` 放 B9 當日情境素材——每日輪替、無因果關係、不記錄玩家進度。主線劇情放 `story/`——一次性、有前置鏈、寫入 `players_story_progress`。同一個地標的兩種內容都存在，但走不同的表與不同的生成路徑，不要混在一起寫。

## 1. 一條 arc 開始之前：確認前置

照下表逐項確認。**任何一項是 ❌，先把它排進時程，不要邊寫劇情邊假設它會好。**

| # | 前置 | 怎麼確認 | 缺了會怎樣 |
|---|---|---|---|
| 1 | 這條 arc 涉及的每個地標，`brain.landmark_souls` 都有內容 | 對應的 `landmark/*.md` 範本表格不是空的 | 人格卡沒有史實素材，靈魂講不出這個地方的事 |
| 2 | 每個地標都有 `active=true` 的人格卡 | 查 `brain.character_personas` | 對話會走 fallback，劇情指令進不了 prompt |
| 3 | 每個地標都有 `spirits` 記錄 | 查 `public.spirits` | 玩家召喚不到這個靈魂 |
| 4 | arc 入口地標的 `sense_radius_m` 已設定且經實地確認 | 查 `public.spirits` | 入口感應範圍不合現場，信發不出去或太早發 |
| 5 | 實地勘查已完成（若含拍照任務） | — | 任務點位全是暫定值，之後要整批重寫 |

第 4 項的做法在萬華 arc 定案後改過：**arc 入口改用「入口地標的 150m 感應驗證」，不用行政區多邊形圍欄。**

原因是圍欄換到的只是「早幾百公尺拿到入口道具」，代價卻是一整套新機制：`brain.districts.boundary` 的 GeoJSON、`check_player_in_district()`（目前刻意未實作）、客戶端第三種前景判定，以及一支新的區界驗證端點。`/sense` 這條路上的到場驗證、token 與去重全部現成。

`district_id` 仍然有用，但只在**伺服器端**：限制 `next_target` 只能是同區地標。那是資料範圍檢查，不需要玩家端圍欄。

> 若未來某條 arc 真的需要「進入某區就觸發」（例如沒有單一入口地標的區域），再回頭補 `boundary` 與 `check_player_in_district()`。屆時第 4 項換回圍欄版本。

## 2. 撰寫步驟

### Step 1｜確定 arc 的識別與範圍

- `arc_id`：`arc_{區域}_{主題}`，全小寫英文，例如 `arc_wanhua_aming`
- `district_id`：這條 arc 綁哪一個區域圍欄（若不用圍欄則留空，但那樣就沒有入口道具機制）
- 涉及的地標清單，以及每個地標在敘事裡的**語氣定位**

語氣定位要寫，而且三個以上的靈魂**必須彼此不同**。同一條 arc 裡如果每個靈魂都用同樣的態度講同一件事，玩家跑三個點只是在收集資訊，沒有情感層次。以「阿明的遺願」為例：龍山寺是淡然的旁觀、紅樓是好奇的收藏癖、剝皮寮是切身的痛——三種距離感。

### Step 2｜寫大綱與核心反轉

一句話大綱 + 核心反轉各寫一段。反轉不是必要的，但如果有，要在這一步就定下來——它決定了每個 beat 該藏什麼、該露什麼。

### Step 3｜設計 beat 鏈

這是整份 SOP 最容易出錯的一步，規則見 §3。

先畫因果圖再填表格。圖上每個節點是一個 beat，每條箭頭是一個 `prerequisite_beat_ids` 項目。畫完之後檢查：有沒有節點沒有入邊也不是起點（那就是永遠觸發不了）、有沒有兩個節點互相指（那就是死鎖）。

### Step 4｜填 `story_beats` 表格

每個 beat 一列，欄位如下：

| 欄位 | 內容 | 注意 |
|---|---|---|
| `beat_id` | `beat_{地標}_{階段}` | 全 arc 唯一，且要能跨 arc 唯一（主鍵是全表的） |
| `character_id` | 對到 `brain.characters` 的**實際值** | 不要寫佔位字串，見 §4 |
| `sequence_order` | 該角色內的順序 | 跨角色可以重複，見 §3.4 |
| `trigger_condition` | 描述性文字 | **必須可判定**，見 §3.1 |
| `narrative_directive` | 敘事指令 | **不是台詞**，見 §3.3 |
| `prerequisite_beat_ids` | 前置 beat 清單，可跨角色 | 見 §3.2 |
| `required_item_ids` | 需持有的道具 | 對到 `player_inventory.item_id` |
| `contingency_notes` | 條件未滿足時怎麼回話 | 見 §3.5 |
| `one_time` | 是否只觸發一次 | 幾乎永遠是 `true`，見 §3.5 |

### Step 5｜設計 `resonance_unlockables`（選用）

跟 beat 鏈**分開的另一條線**：beat 是事件驅動（做了什麼才觸發），unlockables 是數值驅動（共鳴值到門檻就開放）。兩者不互相取代，也不要做雙重門檻（`citysoul_data_schema.md` §8：主線進度為事件驅動，完全獨立於 resonance 機制）。

門檻只能用固定的 **10 / 40 / 100**（AC5.3），不為個別 arc 另訂數值。

建議每個靈魂各留一則「比主線更私人」的片段——主線講的是阿明，unlockables 講的是這個靈魂自己對阿明的感受。這個區隔讓兩條線的存在都有理由。

### Step 6｜內容安全對照 + 前置相依表

- §12.2 逐條檢查（宗教場域必做），格式見 `wanhua_district_storyline_aming_no_landmark_photo_v0.2.md` §6
- 硬前置清單（§1 的表格填實際狀態），放文件末尾

### Step 7｜命名與存放

- 檔名：`{區域}_district_storyline_{主題}_v{版號}.md`
- 存放：`story/`（B9 當日情境素材放 `event/`，見 §0 註記）
- 版號在檔名裡，改版另存新檔，舊版由 Lead 決定何時刪

**檔名一律用英文小寫加底線，不用中文。** 內容可以是中文，檔名不行——中文檔名在跨平台工具鏈上會踩到編碼問題（Windows 用 Big5／UTF-8 不一致、git 預設把非 ASCII 路徑轉義成 `\344\270\273` 這種八進位、CI 容器的 locale 常常不是 UTF-8）。這跟 SDD §7.3.1 對技術命名的要求是同一個理由的延伸。

## 3. beat 設計的五條硬規則

### 3.1 `trigger_condition` 必須可判定

判斷邏輯在 **body 狀態機**（`citysoul_data_schema.md` §9：「`trigger_condition` 的實際判斷邏輯在 body 狀態機，brain 只負責被觸發後該怎麼講」）。狀態機只能查資料庫狀態——它讀不出玩家在對話裡說了什麼。

| ✅ 可判定 | ❌ 不可判定 |
|---|---|
| 玩家首次與某靈魂對話 | 玩家表現出對某件事的興趣 |
| 某 `quest_id` 在 `quest_progress` 中為完成 | 玩家在對話中提及某個關鍵字 |
| 玩家持有某 `item_id` | 玩家語氣friendly |
| 某 beat 完成後的下一次對話 | 玩家猜到了真相 |
| 共鳴值達到某門檻 | 玩家問了正確的問題 |

右欄那些要判就得靠 LLM 做意圖辨識，那違反了 brain／body 的分工，而且不可靠——同一句話今天判得出來、換個模型版本就判不出來，玩家會卡在一個沒有任何錯誤訊息的地方。

**寫出右欄那種條件時，通常代表你想表達的其實是一個前置 beat。** 把它改寫成前置關係。

### 3.2 前置鏈是圖，要當圖來檢查

`prerequisite_beat_ids` 不限制只能引用同一個 `character_id` 底下的 beat（`citysoul_data_schema.md` §9），所以整條 arc 的 beat 構成一張有向圖。三件事必須人工確認，匯入器也會擋：

1. **無懸空引用**：每個引用到的 `beat_id` 都存在。打錯一個字 → 那個 beat 永遠解不開，沒有任何錯誤訊息。
2. **無環**：A 需要 B、B 需要 A → 兩個都永遠觸發不了。
3. **無孤島**：每個 beat 都要從某個起點（無前置的 beat）走得到。

### 3.3 `narrative_directive` 是指令，不是台詞

寫「要講什麼、用什麼語氣、要避開什麼」，不寫成品字句。腦袋據此組 prompt 生成實際對話。

```text
❌ 「我記得他。那孩子每次來，都站在同一根柱子旁邊，一句話也不說。」
✅ 「敘述兩次見到阿明的經過；語氣淡然帶憐惜；不得用『神明告訴我』交代資訊來源」
```

寫成台詞的三個壞處：每個玩家看到一模一樣的字、繞過了 relationship_stage 的深度限制、語氣層無法生效。

**`brain.resonance_unlockables.content` 也是指令**，儘管欄位名叫 `content`——這一點在 schema 文件裡沒有寫明，是最容易搞錯的一個欄位。

唯一真的寫成品字句的地方是 `brain.canned_greetings.response_text`，那是刻意的（B12 快速問候，AC7.1）。

### 3.4 `sequence_order` 是單一角色內的排序

MVP 採單一角色內線性排序（`citysoul_data_schema.md` §8）。所以同一個 arc 裡，三個地標的第一個 beat 都是 `sequence_order = 1`，這是正確的。

唯一性的單位是 `(arc_id, character_id, sequence_order)`。跨角色的順序由 `prerequisite_beat_ids` 表達，不由這個數字表達。

### 3.5 「狀態」不是 beat，`one_time` 幾乎永遠是 `true`

想寫一個「條件還沒滿足時靈魂怎麼回話」的節點時，停下來——那不是 beat，是 `contingency_notes`。

判準：**這個節點有沒有東西依賴它？** 沒有任何 `prerequisite_beat_ids` 指向它，它就不是劇情推進的一環，只是一種語氣狀態。

技術上的理由也一致：`players_story_progress` 的主鍵是 `(player_id, beat_id)`，一個 beat 對一個玩家只能記錄一次。`one_time = false` 在資料上沒有地方表達「觸發了幾次」，寫了也是虛設。

## 4. `character_id` 命名

必須對到 `brain.characters` 的實際值。寫佔位字串（`char_longshan` 這種）的成本是：之後有人照著文件寫 YAML，匯入時才發現外鍵插不進去。

慣例是 `{地名}_{英文角色定位詞}`——**地名取短的那一段，不重複整個 `spirit_id`**。既有值是 `longshan_watcher`，不是 `longshan_temple_watcher`。

定位詞用**角色在敘事裡的功能**，不用角色暱稱或人名——SDD §7.3.1：角色名可能變更，不得進入技術命名。

角色還不存在時，在表格裡明確標記「建議名 / 尚未建立」，不要讓它看起來像既有值。

## 5. 內容治理

### 5.1 §12.2 逐條檢查（宗教場域必做）

用一張表逐條對照，格式見 `wanhua_district_storyline_aming_no_landmark_photo_v0.2.md` §6。五類禁忌：教義解釋、神祇位階、靈驗與否、占卜結果、宗教比較。

**「敘事背景引用」與「玩家真的在問」是兩回事。** 劇情裡提到「拜月老還願」是背景，不是靈驗判定；但玩家看完劇情後問「那我拜了會不會靈」就是禁忌範圍。劇本本身不需要為此調整，但要在文件裡標出來，讓腦袋 B4/B5 的攔截邏輯知道要分辨這兩種情境。

### 5.2 稱謂：城市靈魂用「祂」

指稱城市靈魂一律用**祂**，不用「牠」，也不用「它」。

「牠」是動物用字，「它」是無生命物件。城市靈魂是地標的擬人化集體意識——寫成
「牠」會把一個有記憶、會思念的存在降級成生物，而那跟整個世界觀的前提相反。

這條規則涵蓋所有文件：劇情敘事指令、人格卡、研究記錄、以及程式碼註解。玩家看
不到 `narrative_directive` 的原文，但**模型看得到**，用錯字會影響它對角色的定位。

### 5.3 不寫括號裡的舞台指示

角色講的每一句話都是**直接說出口的話**，不是劇本。不要寫這種東西：

```text
❌ （城市靈魂安靜地看著你）……這件事我還沒想清楚。
✅ 這件事我還沒想清楚。
```

兩個理由。**技術上**：這些文字會原樣送進 TTS 被唸出來，玩家會聽到有人念「左括號
城市靈魂安靜地看著你右括號」。**敘事上**：括號是把鏡頭拉遠去描述角色，而這個
遊戲的前提是玩家正站在祂面前跟祂說話——描述破壞了在場感。

這條規則涵蓋所有玩家看得到的文字：`canned_greetings`、安全婉拒台詞、各種
fallback、解鎖敘事的預寫版本。

**也要寫進 `narrative_directive`。** 模型會把人格卡的 `speech_style`（「溫和、
不疾不徐」）當成要演出來的東西，於是每則回應都以「（微風輕拂，聲音溫和而
悠長……）」開頭。那是實際發生過的事，修法是在 prompt 裡明講不要。

### 5.4 兩個最常滑進去的地方

| 風險 | 為什麼會發生 | 怎麼改 |
|---|---|---|
| **靈魂扮演真人** | 劇情需要一個「認識死者的人」，最自然的寫法就是讓靈魂當那個人 | 改成「那個人在集體記憶裡的樣子」的投影。靈魂自己也說不清那是不是本人——這通常比原版更貼合「地標集體意識」的設定 |
| **靈魂轉述神明的話** | 需要交代靈魂為什麼知道某件事，「神明告訴它」是最省事的解法 | 把資訊來源錨定在靈魂自身的**在場與觀察**：「我剛好在旁邊，聽見了」 |

兩者都是 SDD §3 Avoid 清單的直接違反，敘事審查一定會擋。**在草案階段就改，不要等審核退件**——它們通常只影響「怎麼講這句話」，不影響劇情骨架，早改成本極低。

### 5.5 目前沒有審核欄位

`character_personas` 有 `active` / `reviewed_by` / `reviewed_at`，改人格要 append 新版本並重新審核。

**`story_beats` 與 `resonance_unlockables` 沒有這三個欄位**（`citysoul_data_schema.md` §8/§9 的設計如此）——匯入就直接生效。但 `narrative_directive` 同樣會注入 prompt，內容治理風險與人格卡同級。

在 schema 補上之前，審核只能靠流程：**Lead 過目 → 才產 YAML → 才跑匯入器**。要不要補欄位是待決事項，見 `wanhua_district_storyline_aming_no_landmark_photo_v0.2.md` §9.2。

## 7. 常見誤區

- **把「玩家說了什麼」寫進 `trigger_condition`**：最常見的一個。想寫的時候，通常代表那應該是一個前置 beat。

- **前置條件寫得太保險，造成遞移冗餘**：`C ← B ← A` 的情況下，C 不需要再寫一次 `A`。多寫不會出錯，但會讓因果圖看起來比實際複雜，之後改劇情時容易漏改。

- **把語氣狀態當成 beat**：判準是「有沒有東西依賴它」。沒有就是 `contingency_notes`。

- **`narrative_directive` 寫成台詞**：寫的時候會很有成就感，因為看起來就像成品。但它繞過了語氣層與深度限制，而且每個玩家會看到一模一樣的字。

- **假設地標會準時就緒**：主線需要三個靈魂，但 DB 裡可能只有一個，而且那一個的人格卡還沒過審核。寫劇情之前先查一次實際狀態。

- **把地理圍欄當成「之後補」**：沒有 `boundary` 多邊形，圍欄恆為 false，入口道具發不出去，整條 arc 沒有入口。

- **為主線另訂共鳴門檻或給分**：門檻固定 10/40/100，任務完成固定 +20，收藏固定 +10（AC5.1–5.3）。主線不開特例。

- **等內容全部齊備才建表**：建表跟填內容是兩件事。空表無害，早建早撞問題；等內容完成才建表，每個 schema 問題都會變成一支要改既有資料的 migration。
